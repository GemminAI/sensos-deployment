### 3.1 The one failure: contract mismatch with the pinned MSR

`test_geometry_is_measured_only_when_msr_imports` calls `geometry.emit_single(..., contract_version="1.1.0")` and fails with
`TypeError: unexpected keyword argument 'contract_version'`. The pinned meaning-space-runtime `ee26c7c` has no such argument.
The commit that adds it (`f36b15d`, "add contract_version and default IC-00 to 1.1.0") was contained only in a local branch of
the maintainer's checkout when this was checked; no remote-tracking branch contained it.

Consequence: the public nvs-runtime 1.0.0 tests assume an MSR commit that the Core Release Manifest does not pin. The pin
was **not** changed (the verified release configuration stays fixed). This test is reported as failed and is not counted
as passed.

The same test first skipped, because it looks for an MSR checkout at a hard-coded path under the home directory. For the
run it was pointed at the installed MSR through a throwaway `HOME` containing one symlink; nothing outside `/tmp` was touched.

## 7. Follow-up runs, same day (after the first record)

Host: the same Parallels VM (aarch64, Ubuntu 24.04.3, Python 3.12.3). Code: `feature/installer-linux-cpu` at `738d054`.

### 7.1 Formal Store reuse compares the whole declaration (commits `7dd2281` to `260e5c5`)

- Why: the first Installer decided the generation of a store by the catalogue hash alone. Two stores with the same catalogue but another
  `accepted_versions` have different declaration hashes and judge the same envelope differently (shown on throwaway stores at hekb-vnext
  `5943a8d`). Identity is checked on the whole declaration; the Installer now does so.
- Check: a store of the right generation is reused only if its `declaration.json` equals the declaration `formal_declaration` makes from the
  pinned hekb-vnext and the measured catalogue. Otherwise the install stops (`declaration-mismatch`, with the differing fields).
- Real machine, existing store made by the earlier Installer (`/tmp/sensos-chain-home`): `status: reused`, `declaration_match: match`,
  declaration sha256 `f12dbda73e8f4797fd50e5ceeaa545583df7f2ba7e3cdb1278e6edeb2268da72`.
- Real machine, new home: first run `created` (checks 1 to 7 pass); later runs `reused`, `match`.
- Not run on a real machine: the mismatch stop (covered by a unit test only).

### 7.2 Check 1 failed in the chain-test home: not an Installer fault

The home used for the chain tests had `pytest` and four dependencies added to its venv. Check 1 (version lock) reported them as
installed but not in the lock, and failed. Repository HEADs and the two wheel hashes matched the manifest. The check did what it is for;
the chain-test home is not a clean Installer result, and no claim in section 2 rests on it.

### 7.3 Two runs in the same second collided (fixed in `387fcc3` to `738d054`)

- Symptom: on a new home, a second install run right after the first failed check 7 (`formal_store_not_empty`). It also failed with the
  code before these changes (`766f9ee`); a third run later passed.
- Cause: the throwaway store of check 7 was in a folder named by the UTC second. A run takes about one second, so two runs could share
  the folder, and hekb-vnext correctly refuses to create a Formal Store in a non-empty folder. hekb-vnext is not at fault.
  The report file names (`failed/`, `redeploy/`) had the same second-level names and the second report would have been lost.
- Fix: folders and report files are created exclusively and get `-001`, `-002` ... on a clash. Nothing existing is overwritten or reused.
- Real machine, new home, three installs in a row: all exit 0, checks 1 to 7 pass each time. `acceptance/` holds
  `20261125T062854Z`, `20261125T062854Z-001` and `20261125T062855Z` (the first two runs reached check 7 in the same second);
  `reports/` holds `deployment.json` and two files in `redeploy/`.
- Not run: two Installer processes at the same moment (not an intended use); the Python tests were run by Claude Code, not by hand on the VM.
